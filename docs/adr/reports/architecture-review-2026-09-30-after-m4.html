Problem

The Wave's rules are private state and helpers spread through the Game. The Game also prices Ink, tracks what was paid, keeps undo and answers looks. The Core Zone rule is written at five sites and its refusal order twice. "Ink Core destroyed" is decided in three modules, and one of them is the Sandbox world, below the Game. Every Wave test runs a real Game over Box2D. Milestone 5's loop is all phases, and the only place for it today is this Game.

Solution

A Wave module in src/game/ holds the phase, the arrivals, the end, the Core Zone and the lose rule. The Game asks it whether a Stroke may be drawn and whether undo is allowed, and hands it each step. The Sandbox world stops refusing to start. The HUD and the Core Zone drawing read the Wave's reading. The Game's step and advance share one way of running the step hooks.

Wins
  • locality: phases in one module
  • lose rule gets one owner
  • Core Zone rule: 5 sites → 1
  • M5 loop lands in one place
  • Wave tested without Box2D
  • Game shrinks to Ink and undo
This settles a replay invariant that is written twice. Game.step (game.ts:674) repeats by hand the before, step, after order that SandboxWorld.advance runs (sandbox-world.ts:798), and exact replays depend on that order.

Problem

The scene loads a demo through Game.clear(build, wave, terrain). The gallery tests load it through loadDemo, which builds on the Sandbox world and never sees the Game. Demo.wave is declared, set by no demo and tested nowhere. Milestone 5 adds three arenas, each with its own Terrain, sequence of Waves and Tank amounts. Each would become another positional argument on a path the tests don't run.

Solution

An Arena description names everything an Arena starts with. One Game call loads it: clear, Terrain, Waves (handed to C1's Wave), Tanks, then the build. The gallery demos, the sandbox Arena and milestone 5's arenas are all descriptions. The tests load them the same way the scene does.

Wins
  • interface: one load, one argument
  • tests cross the played seam
  • leverage: arenas are data
  • dead Demo.wave path goes
Gallery demos and stress tests are free, and ADR 0009 keeps it that way. The description has to keep that: a build still runs below the Game at price 0, as clear(build) runs it today.

Problem

The Material rules decide Pressing, but the "stalled" fact it depends on is worked out inside the Enemies kind. "Is it dead" is written twice, and one copy is dead code. Ten of the port's 27 members exist only for Enemies. Every rules test pays for a 352-line fake. The Siege Walker is a multi-legged heavy walker, and it would widen both halves.

Solution

One Enemy rules module owns walking, stalled, Pressing, hurting, reaching the Ink Core, deaths and Drops. The Material rules keep the one step order from #75 and call into it at the two points they already have. Its port holds only what Enemies need.

Wins
  • locality: an Enemy's life, one module
  • Material rules port: 27 → ~17
  • one "dead" rule
  • Siege Walker lands in one place
This is Worth exploring rather than Strong because the Material rules are already deep, with two methods behind their step, and the full-world Enemy tests cover the behaviour. It pays off when the Siege Walker is specced. Delete the dead isDead in enemies.ts:177 now, whatever you decide.

Problem

The renderer takes the world, the Core Zone drawing takes the Game, and the scene joins the two. The tuning panel edits tables that belong to the world while going past the Game. The HP bar maths is copied into two drawings.

Solution

The Game hands out one reading of what to draw, the world's and the Wave's together, and one set of tables to tune. The HP bar becomes one shared drawing.

Wins
  • one render input
  • one HP bar
This is Speculative: nothing is wrong today, and the render budget test guards drawing. Revisit it after C1, when the Aftermath and the Analysis need drawing.
Also noticed, not candidates
  • A Pit keeps what isn't an Enemy. kill() only acts on the Enemies that belowScreen() returns (material-rules.ts:446). Rubble and Objects that fall into a Pit keep falling and simulating forever. The spec doesn't say what should happen to them. Ask before milestone 5 puts Pits in real arenas: should they be removed as they are over the Spawn edge?
  • Spawn stand position is computed twice in enemies.ts (201–205, 218–221), and the Ink Core's centre is computed twice (enemies.ts:252, game.ts:281). These are small copies that could drift.
  • drops.ts fails the deletion test, since deleting it would only move its code. It is harmless. If C3 happens, fold it into the Enemy rules module.
  • Sandbox world is shallow for its size: about 15 forwarding getters and a 95-line constructor of wiring. Its depth is in snapshot, rebuild and step. C1 and C3 each take a little out of it, so it isn't a candidate of its own.
Top recommendation

Give the Wave its own module

Milestone 5 is the defence loop: Analysis, Build Phase, Wave, Aftermath, in sequences. Every part of it is a phase rule, and today the only place for one is an 878-line Game that already does four jobs, with the lose rule split across three modules. Pull the Wave out first, then do C2 so arenas load their Waves into it.
